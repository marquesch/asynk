# asynk core — design

Date: 2026-11-02
Status: draft, awaiting approval

## Intent

asynk is an asyncio-based framework for background tasks in Python, similar in feel to Celery
(an `App`, tasks registered with `@app.task(...)`, `task.delay(...)` from anywhere), but with
producers and consumers fully decoupled. The user can write their own producer and their own
consumer, and the two never need to know about each other. Only the **envelope** (the shape of a
task message) is shared.

Motivating case: a producer that writes a row into a Postgres `outbox_event` table (ideally in the
caller's transaction), an external outbox relay that publishes the row to RabbitMQ, and an asynk
consumer that reads the RabbitMQ message and runs the task. Celery cannot express this.

## Goals

- Decoupled producer and consumer, each a small interface the user can implement.
- `@app.task` registry; `await task.delay(*args, **kwargs)` typed so that static checkers and
  LSPs see the task function's own signature.
- Canonical envelope plus pluggable codec. Producers and consumers own their wire encoding.
- Single-process asyncio worker, designed for Kubernetes: graceful SIGTERM drain, liveness and
  readiness probes as first-class concerns.
- Hook-based failure handling (retry, DLQ, etc. live in hooks / producers / consumers).
- Stdlib only in the core. Python >= 3.14 (already set in `pyproject.toml`).

## Non-goals (v1)

- Real broker integrations (RabbitMQ, Redis, Postgres listen/notify). Planned later as optional
  extras (`asynk[rabbitmq]`, ...). Not in v1.
- Result backend / fetching task results. Out of scope.
- Task cancellation. Out of scope, but `delay` returns the producer's handle so it can be added.
- Master/worker process management (Celery-style forking). Explicitly rejected: k8s scales pods.
- A built-in retry policy. The core only provides the pieces (see Failure handling).
- Rich argument types. Arguments must be JSON-friendly (primitives, lists, dicts, None).

## Anti-goals

- Coupling a producer to a specific consumer or transport.
- Hardcoding retry/DLQ behavior in the core.
- Third-party dependencies in the core.

## Components

### App and task registry
- `App(name, producer=...)` holds the task registry and the configured producer.
- `@app.task(name=None, max_retries=None, **options)` registers a function (async or sync) and
  returns a `Task` object. Task options are general-purpose: hooks may read them, but they are
  not hook-specific. The core itself reads `max_retries` to decide when to call
  `max_retries_exceeded_hook`.
- Default task name is derived from module + qualname; overridable.

### Task and typed `delay`
- `Task` is generic over `ParamSpec` and return type. `delay` is typed with the same `ParamSpec`
  so checkers validate arguments against the original function's signature.
- `delay` is a coroutine: `handle = await task.delay(1, b=2)`.
- It builds an `Envelope`, passes it to the app's producer, and returns whatever the producer
  returns (task ID / row ID / handle). Nothing more is done with it in v1.
- Calling the task directly (`task(...)`) runs the underlying function unchanged.
- Argument validation: arguments are checked to be JSON-friendly at `delay` time (fail early).

### Envelope
Immutable dataclass: `id` (UUID string generated by asynk), `task` (name), `args`, `kwargs`,
`attempt` (int, starts at 0 or 1 — builder to pick and document), `metadata` (dict of
JSON-friendly values; for producers/consumers/hooks to use, e.g. headers, timestamps).
The `id` is generated by asynk before the producer runs, so it exists even when the outbox
row is only flushed on transaction commit.

### Codec
Protocol `Codec` with `encode(Envelope) -> bytes` and `decode(bytes) -> Envelope`. A default
JSON codec (stdlib `json`) ships in the core. Producers and consumers take a codec; users can
supply their own (e.g. a string-wrapped JSON for an outbox column).

### Producer and Consumer interfaces
- `Producer` protocol: `async def publish(envelope: Envelope) -> Any`.
- `Consumer` protocol: an async source of deliveries. Each delivery exposes the decoded
  `Envelope` plus transport-specific ack/reject operations, and consumers may wrap per-message
  handling in an async context manager that provides default ack-on-success / reject-on-error
  behavior when no hook takes over. Exact shape is left to the builder; it must allow:
  start/stop, iterating deliveries, ack, reject (with requeue flag).
- v1 ships one crude producer/consumer pair (in-memory using `asyncio.Queue`; a unix-socket pair
  is optional) to prove the interfaces and to test the core without a broker.

### Worker
- One asyncio process: `Worker(app, consumer, concurrency=N, hooks=...)`.
- Pulls deliveries, looks up the task in the registry, runs it concurrently up to `concurrency`
  (semaphore). Async tasks are awaited; sync tasks run via `asyncio.to_thread`. No other sync
  machinery.
- Graceful shutdown: on SIGTERM/SIGINT stop pulling, wait for in-flight tasks (with a
  configurable timeout), then exit. Unknown task name is treated as a failure with a distinct
  status.
- Probes are **file-based** (owner's decision). The worker runs a heartbeat task on the event
  loop that periodically rewrites a liveness file (containing a timestamp), so a stale file means
  the loop is blocked or dead. A readiness file exists only while the consumer is connected and
  the worker is not draining; it is removed on shutdown start. File paths (default under a
  configurable directory, e.g. a tmp dir) and heartbeat interval are configurable.
- Checking: a small stdlib-only entry point (e.g. `python -m asynk.health liveness|readiness
  --max-age N`) reads the files and exits 0/1, for use as a k8s `exec` probe. Stale or missing
  file means failure.
- Other probe mechanisms (e.g. an HTTP endpoint) may be added later; the probe state is kept
  behind a small interface so they can be added without touching the worker loop.

### Failure handling and hooks
- After each task the worker builds a result record: envelope, `TaskStatus` enum (e.g. SUCCESS,
  FAILED, RETRIES_EXCEEDED, UNKNOWN_TASK; builder may refine), the return value or exception.
- A general `after_task` hook receives that record and is responsible for ack/reject of the
  delivery. A specific `max_retries_exceeded_hook` is called by the core when
  `envelope.attempt` exceeds the task's `max_retries`.
- If no hook handles the delivery, the consumer's per-message context manager applies its
  default ack/reject.
- Retry mechanics are NOT in the core. A retry is a producer/consumer matter: e.g. a hook asks
  the producer to republish a new envelope (attempt + 1) and then acks the original, or the
  consumer nacks with requeue.

## Engineering rules (from the project owner)

- TDD: failing test first, always. pytest + pytest-asyncio (already in dev deps).
- uv for everything (`uv add`, `uv run`).
- Static checks: ruff (lint + format) and mypy (strict). Both added as dev dependencies.
- Any new technology or dependency must be asked about before being added.
- Git: Conventional Commits; never a Co-Authored-By trailer; always work on branches (the owner
  merges via the GitHub UI).

## Decisions I made (not yet confirmed by the owner)

- The probe-check entry point is `python -m asynk.health` using stdlib `argparse` (the file-based
  approach itself is the owner's decision).
- Default JSON codec lives in the core.
- Concurrency via an asyncio semaphore; default concurrency value is the builder's choice.
- Task IDs are UUID4 strings generated by asynk.

## Left to the builder

- Exact Consumer/Delivery protocol shape and the context-manager ergonomics.
- Exact `TaskStatus` members, `attempt` base (0 or 1), module layout under `src/asynk/`.
- Whether the v1 demo transport also includes a unix-socket pair.
- Hook registration API (decorators vs constructor arguments).
